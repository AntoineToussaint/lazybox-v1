# React surfaces

`AgentWindow` is the public component: give it a resolved Runner connection and optionally an initial agent (Claude by default), working directory, or existing session ID. It owns authentication, discovery, session startup/attachment, event subscriptions, messages and generic file uploads (including native image input), request cards, interruption, and a command-output drawer. Drop files anywhere in an active chat to add them to the draft; dropping does not send. The picker and drops share Runner-advertised limits and the same byte-upload path. Folders are rejected. `make test-attachments` checks embedded, detached, and standalone composers with fake RPC. Enter sends; Shift+Enter inserts a line; IME confirmation does not send. Unmounting disconnects readers without stopping execution. The host owns URL persistence and native window creation through optional callbacks. See [usage](../../../RUNNING.md#reusable-agent-window).

Work graph, previews, review, and native desktop surfaces remain future work.

Conversation navigation uses creation time with a stable ID tie-breaker. Choosing a row only changes the view; it does not refresh the Runner catalog or reorder conversations. A detached chat appears as a compact return control instead of reserving a blank pane. Older Runners expose live conversations, with an explicit notice that saved history requires a Runner update.

## Attention inbox

The header's **Inbox** (`] ] i`) lists every work conversation of the Runner, across workspaces, grouped by what it needs: *Needs input* (a pending question or approval), *Failed* (a fault, a provider failure, a failed delivery, or a turn a Runner restart interrupted), *Ready for review* (a turn ended since you last looked), *Working*, and *Done*; newest first within a group. Each row shows the workspace, agent and model, age, and the agent's last line (`Session.last_message`) or the pending request. `j`/`k` move, Enter opens the conversation in its workspace, `m` marks it seen. The count on the entry is what needs you: needs input, plus unseen failures and finished turns. Sidebar rows carry the same unread marker. Assistant panels ("Ask Lazybox") are not work items and are left out.

The state is a pure function (`attention.ts`, tested in `scripts/attention.test.ts`). *Seen* is local: a mark per conversation in localStorage under the Runner authority, shared live by every window of that Runner, so reading a conversation in a detached chat window clears it in the main window too. A conversation counts as seen while it is on screen in a focused window. The first look starts the record: turns that ended before it are not news.

Notifications come from the one window whose host can show them (the desktop main window; the main browser view): an entry into *Needs input* (each new request) or *Failed*, and optionally *Ready for review* (Settings → Notifications). Only a change that window watched, with new agent activity behind it, notifies — the first observation is a baseline, so a Runner restart that re-labels state without the agent doing anything never notifies — and never for the conversation you are looking at. While that window is in front the notice is an in-app toast (bottom right, with Open and the ⌘J hint) instead of a system banner; in the background it is a system notification. A burst becomes a summary. The dock badge counts conversations that need input. Clicking a notification or a toast opens its conversation. A short synthesized sound (Web Audio, no audio files: `sounds.ts`) plays for *needs you* (input or a failure, on by default) and for *done* (a finished turn, off by default), switched and previewed in Settings → Notifications → Sounds. `npm run test:inbox` and `npm run test:command-palette` drive this against the fake Runner.

## Context menus

Inside the app a right-click opens a Lazybox menu for that place, never the browser's or macOS's; a long press on touch, Shift+F10 or the context-menu key on the focused element open the same menu. Arrows, Home/End, typing the start of a label, Enter and Escape work as in a native menu; a press outside, scrolling, leaving the window or Escape closes it, and one is open at a time. Text fields keep the native menu (spelling, paste, emoji); the Monaco editor keeps its own, in Lazybox colours; Alt+right-click shows the native menu in development, for Inspect Element.

A menu is assembled from sections, innermost first: Copy when the click is on a text selection, then each place under the pointer that declares a menu (a code block's items, then its message's). Where nothing declares one it offers Reload window. Wired: chat messages (quote in reply, copy, copy as Markdown, jump to prompt, the turn's checkpoint actions), agent turn markers, code blocks, web links, file references, Files rows, editor tabs, panel headers, the chat header (the ⋯ session actions), workspace and conversation rows (their ⋯ items, from the same list), Changes rows and diff lines (open, copy paths, add a review comment), processes, command output (stop, run again, copy the command or output), the terminal (copy, paste, select all, clear, send selection to agent) and Inbox rows. The desktop app adds Reveal in Finder and, in development, the inspector.

Features add items without editing the place that declares the menu: `registerContextMenu(scope, context => items)` or `useContextMenuContribution`. The scopes, the `detail` each receives and the item format are documented in the header of `ContextMenu.tsx`. The model (placement, keyboard, type-ahead) is pure and tested in `scripts/context-menu.test.ts`; `npm run test:context-menus` right-clicks every wired place in WebKit against the fake Runner.

## Actions, keys and the command palette

Every command is declared once in `actions.ts` (id, title, group, icon, default keys, scope). Components register what an action does with `useAction`/`useActions` (or the older `useKeyboardAction`), optionally with a when-enabled predicate; `runAction(id)` runs it. The keymap (`keyboard.ts`), the `]]` which-key card, the command palette, the shortcuts overlay, the desktop menu bar (`nativeMenuItems`, published by the main window through the `set_action_menu` command and rebuilt when keys change) and context menus (`actionsFor`, `actionMenuItems`, which return items in `ContextMenu`'s shape) all read it.

Keys: a chord such as `Mod+k` (⌘ on a Mac, Ctrl elsewhere) fires from anywhere, text fields included, except chords the file editor owns (⌘K, ⌘/, ⌘[ …) while it has focus and Ctrl chords in a terminal. Sequences (`] ] i`) and bare keys (`?`) fire outside text fields, and a bare key typed in the message box stays text. A value may list alternatives with `or`. Keymaps saved before the registry (no `__version`) keep every saved key and gain the new actions' defaults in the saved leader, minus any key that would collide with a saved one or with an entry of the person's own `]]` menu (`migrateKeymap`).

The palette (⌘K or ⌘⇧P, `] ] p`) searches actions, conversations in every workspace, workspaces, files (Go to file's search), settings sections, panels, artifacts and missions; empty, it shows recent choices, what needs you, and all actions. `>` narrows to actions, `@` conversations, `#` workspaces, `/` files. In a detached chat window, going somewhere asks the main window (through localStorage, like attention) and brings it forward. The shortcuts overlay (`?`, ⌘/) lists every action with its keys, filterable, with Customize… to Settings → Shortcuts. Navigation: ⌘1…⌘9 the Nth workspace of the sidebar, ⌘J / ⌘⇧J the next / previous conversation that needs you across workspaces (needs input, unseen failures, unseen finished turns, in inbox order), ⌘] / ⌘[ the next / previous conversation of this workspace.
